## 2. The architecture that makes all three composable — build this first

Today `page.tsx` does everything inline: load rows → `map` each row to a bar → sort → render
([app/calendar/page.tsx:119-141](../../app/calendar/page.tsx)). That is why three features collide
in one file, and it is untestable (`.tsx` is not collected — see §5).

Refactor it into a pipeline, with **every stage except render as a pure function in `lib/calendar/`**:

```
searchParams ──► parseCalendarParams()      → { view, anchorDay, filters }   [pure]
                        │
                        ▼
              loadCalendarData(window)       → { rows, itemNames, groupTitles }  [server, lazy import]
                        │
                        ▼
              buildCalendarBars(rows, itemNames, groupTitles)  → CalendarBar[]   [pure]  ← P11.6
                        │
                        ▼
              applyCalendarFilters(bars, filters)              → CalendarBar[]   [pure]  ← P11.7
                        │
                        ▼
              placeInWeek(bar, weekRange)  per visible week row                  ← P11.5 reuses this
                        │
                        ▼
                     render
```

Suggested module layout (adjust names if you have a better one, but keep the purity boundary):

- `lib/calendar/bars.ts` — `CalendarBar` type, `buildCalendarBars`, `applyCalendarFilters`,
  `parseCalendarParams`. **Pure.** No `server-only`, no DB import, no Next APIs.
- `lib/calendar/month.ts` — month-grid date math. **Pure.**
- `lib/calendar/week.ts` — unchanged except for anything genuinely shared. `placeInWeek` keeps its
  current signature (it takes `{ start_at, end_at }` — `HasInstantWindow`, line 77 — which a
  `CalendarBar` envelope satisfies for free; **do not change that signature**).

`CalendarBar` should carry at minimum: a stable `key`, the envelope `start_at`/`end_at`, the
display `status`, the primary label, the item-name list, the set of `item_id`s it covers (for the
product filter), the `group_id` (nullable → link target), and whatever the tooltip needs.

**Keep the lazy DB import.** [app/calendar/page.tsx:36-42](../../app/calendar/page.tsx) defers
`import("@/lib/repositories/...")` specifically so `next build` runs without `DATABASE_URL`. Any new
loader code — including the batch group lookup — must stay inside that deferred function.

## 3. The deliverables

### 3.1 P11.6 — one bar per reservation group

**Repository (additive, `lib/repositories/reservation-groups.ts`):**

```ts
export async function listReservationGroupsByIds(
  ids: string[],
  client?: Queryable,
): Promise<ReservationGroupRow[]>
```

- `SELECT ${GROUP_COLUMNS} FROM reservation_groups WHERE id = ANY($1::uuid[])` — `id` is `uuid`
  ([db/schema.sql:36](../../db/schema.sql)).
- **Return `[]` for an empty `ids` array without issuing a query.** One round trip, never N+1.
- Match the file's existing style: `executor(client)`, the shared `GROUP_COLUMNS` constant, a short
  doc comment. Do **not** change any existing function in that file.

**Grouping (`buildCalendarBars`, pure):**

- Rows with a non-null `group_id` collapse into **one** bar per `group_id`. Rows with
  `group_id === null` (storefront bookings) each become their own bar, exactly as today.
- **Envelope:** a group's window is `{ start_at: min(rows.start_at), end_at: max(rows.end_at) }`.
  Mon–Tue + Mon–Wed ⇒ the bar spans Mon–Wed. Feed that envelope to `placeInWeek`.
- **Primary label:** the group's `title`. `title` is nullable
  ([db/schema.sql:37](../../db/schema.sql)) — fall back to the first item's name, then
  `"Unknown item"`, never render an empty bar.
- **Item subtitle:** the distinct item names among the group's rows, comma-joined, truncated with a
  `+N` count when too long. The **full** list goes in the native tooltip — extend the existing
  multi-line `title` string at [app/calendar/page.tsx:202-209](../../app/calendar/page.tsx) rather
  than inventing a new tooltip mechanism.
- **Link:** unchanged — `group_id ? <Link href={/reservations/${group_id}}> : <div>`
  ([app/calendar/page.tsx:240-251](../../app/calendar/page.tsx)). It now represents N rows instead
  of 1.
- **Stable ordering.** The current sort (active first, then `startCol`, then earliest start,
  [lines 135-141](../../app/calendar/page.tsx)) must survive and must be **deterministic for a
  group** — ties broken by something stable like `group_id`, never by `Map` iteration order.

### 3.2 P11.7 — filter flyout

**URL contract (filter state lives in the URL, never in `useState`):**

| Param | Meaning | Absent ⇒ |
| --- | --- | --- |
| `?cancelled=1` | show cancelled reservations | **hidden** (behavior change from today) |
| `?items=slug-a,slug-b` | show only bars touching these products | no product filter — show **all** |

An **empty** `items` selection means "show everything", never "show nothing". Parse defensively:
unknown slugs are ignored, a malformed param falls back to the default rather than erroring the
page — same spirit as `resolveAnchorDay` ([lib/calendar/week.ts:192-201](../../lib/calendar/week.ts)).

**Predicate grain — this is the load-bearing bit:** the product filter matches **per bar**, i.e. a
group with 3 items passes if **≥1** of its items matches. Because grouping (3.1) lands first, you
filter `CalendarBar[]`, not `ReservationRow[]`. Never filter rows before grouping — that would drop
a group's sibling rows and silently shrink its envelope and item list.

**Active-filter count badge** on the flyout trigger (e.g. "2") so staff can tell at a glance the
view is narrowed. Count "show cancelled is on" and "N products selected" per the rule you pick;
state the rule in a comment.

**The flyout component** (`app/calendar/filter-flyout.tsx`, `"use client"`):

- Model the open/close behavior on [components/nav/AccountMenu.tsx](../../components/nav/AccountMenu.tsx)
  — `aria-expanded`, Escape closes and returns focus to the trigger, outside-click closes.
- The panel body is a **plain `<form method="GET" action="/calendar">`** with a checkbox for
  cancelled, checkboxes for products, a hidden input preserving the current `week`/`view` params,
  and an Apply button. Submitting navigates with the query params — **no `useRouter`, no client
  fetch, and it degrades to working without JS.** The only client state is "is the panel open".
- The component makes **no security decisions** — say so in its header comment, as `AccountMenu`
  does.

### 3.3 P11.5 — week/month view toggle

**The simplification that makes this small: a month grid is N stacked week rows.** The visible
month grid is 4–6 calendar weeks, each of which is the same 7-column grid the week view already
renders. So `placeInWeek` handles multi-day spanning, clipping, and continuation arrows **for
free**, per week row. Do **not** write a second placement algorithm.

- `lib/calendar/month.ts` (pure) answers only: *which `WeekRange`s make up the visible grid for the
  month containing day N?* — i.e. the Sunday on/before the 1st through the Saturday on/after the
  last day, chunked into `WeekRange`s. Plus `prevMonthIso`/`nextMonthIso` and the month label.
  Build it on the civil-date primitives already imported by `week.ts`
  (`daysFromCivil` / `civilFromDays` / `weekdayFromDays` / `formatDays` / `parseDateToDays` from
  [lib/scheduler/recurrence.ts](../../lib/scheduler/recurrence.ts)) — **never raw millisecond
  arithmetic**; `lib/calendar/week.ts:239-247` explains why that is DST-unsafe.
- **The DB window must cover the whole visible grid**, including the leading/trailing fill days from
  adjacent months — not just the 1st to the 31st. Getting this wrong silently drops bars from the
  first and last rows.
- **`?view=month`; no param ⇒ week.** An existing bookmark must render exactly as it does today.
- **Keep `?week=` as the anchor-date param in both views** (just document it as "anchor civil
  date"). Do not introduce a second date param — existing links keep working, and `Prev`/`Next`
  stay one code path.
- `Prev`/`Next`/`Today` page by the selected unit: by week in week view (existing
  `prevWeekIso`/`nextWeekIso`), by month in month view. Update the `aria-label`s accordingly
  ("Previous month" etc., [lines 158-174](../../app/calendar/page.tsx)).
- The view toggle is two `<Link>`s in the toolbar — **not** a client component. Mark the active one
  with `aria-current`.
- **Per-day overflow:** cap the stacked bar rows per week row (3 is a reasonable default) and render
  a `+N more` indicator in the day cells that overflow. `confirmed`/`block`/`cancelled` styling
  (`statusClass`/`statusLabel`, [lines 74-84](../../app/calendar/page.tsx)) applies in month view
  identically.
- **Both filters and grouping apply in month view too** — that falls out of §2's pipeline for free
  if you built it there, and is the reason this task is third.

## 4. Judgment calls — decide these, don't stall on them

1. **Mixed-status group (asked for explicitly by #14).** Use this precedence and document it in a
   code comment: a bar is **`cancelled` only if every one of its rows is cancelled**; otherwise
   `confirmed` if any row is `confirmed`, else `block`. Rationale: a paid storefront line item is
   the most consequential thing in the group, and a group with one cancelled line is still a live
   booking.
2. **Should a cancelled line item inside an otherwise-live group count toward the envelope and the
   item list?** No — compute the envelope and item names from the rows that are actually being
   displayed after the cancelled filter. A cancelled chair order should not stretch the bar.
3. **SQL filter vs post-load filter (asked for explicitly by #15).** **Post-load, in pure code.**
   Reason to state in your handoff: the filter grain is per-*group*, so filtering in SQL would drop
   a matching group's non-matching sibling rows and corrupt both its envelope and its item subtitle.
   **Therefore: keep calling `listReservationsInRange(start, end, { includeCancelled: true })` and
   apply *both* filters in `applyCalendarFilters`.** Net effect — you add **no** filter param to
   `listReservationsInRange` at all, which also satisfies #15's "don't change `includeCancelled`
   behavior for other callers". The weekly/monthly dataset is small; this is not a perf concern.
4. **Overflow cap number.** Pick 3 unless the CSS argues otherwise. Don't spend time tuning it; make
   it a named constant so it's a one-line change later.
5. **Scope fence — do not touch:** [app/reservations/[groupId]/](../../app/reservations/[groupId]/)
   (the Edit Reservation page, which also consumes `group_id`),
   [components/nav/nav-config.ts](../../components/nav/nav-config.ts), or any existing exported
   signature in `lib/calendar/week.ts`. `tests/calendar-week.test.ts` must stay green **and
   unmodified** — that is your proof you extended rather than rewrote.
