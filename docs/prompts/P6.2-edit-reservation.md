## 2. Functional requirements (spec §7/§9, made concrete)

Build a **scheduler-or-admin** Edit Reservation page + its server actions.

### 2.1 Load a booking
- The page loads by **`group_id`** (spec §9: "The Edit Reservation page loads a booking by
  `group_id` and shows all its item rows together"). Fetch the group, all its reservation
  rows (`listReservationsByGroup`), and — if the group has a `series_id` — the series row so
  the UI can offer series-level operations.
- Render all line items together, plus contact name/email/phone, notes, title. Show whether
  the booking is a one-off or part of a recurring series (and, for a series, how many
  occurrences / the recurrence summary — read-only is fine).
- If the `group_id` doesn't exist → Next `notFound()` (404). If every row is already
  cancelled, still render (read-mostly) but make the state obvious.

### 2.2 Edit contact info & notes (no capacity impact)
- Editing **contact name/email/phone, notes, title** does **not** change any time window, so
  it must **not** go through the booking engine. Use `updateReservationContact` /
  `updateReservationGroup` inside a transaction. Validate with Zod (mirror P6.1's field
  rules: email format, max lengths, trims).

### 2.3 Edit line items / dates / times (capacity impact) — cancel-then-rebook
- Changing an **item, quantity, date, or start/end time** changes what capacity is occupied,
  so a naive `UPDATE` would bypass the §8 race-safe check and can double-book. **Do it as
  cancel-then-rebook inside ONE transaction:**
  1. `cancelReservationsByGroup(oldGroupId, client)` (frees the old capacity within the txn).
  2. Build the new line set and call `scheduler.createBooking({ ..., groups: [newGroup] },
     client)` — this re-acquires the advisory locks and re-checks capacity for the new
     window(s). Because the old rows are cancelled first *in the same transaction*, the
     recheck correctly sees the freed capacity (no false self-conflict).
  3. If `createBooking` throws `GroupBookingConflictError`, the whole transaction rolls back
     — **nothing changes**, the original booking stays intact — and you surface the conflict
     lines to the UI exactly like P6.1 (`conflicts: ConflictLine[]`, "Nothing was changed.").
  - Preserve the `series_id` linkage when rebooking a single occurrence of a series (pass the
    existing `seriesId` so the new group stays attached to the series). Editing occurrence
    membership finer than "this occurrence" / "the whole series" is **out of scope** (spec
    §9: "Keep it simple — occurrence-level and series-level operations, nothing finer").
  - **Document the cancel-then-rebook reasoning in a code comment** at the action so a future
    reader doesn't "optimize" it into a plain UPDATE and reintroduce the race.

### 2.4 Delete / cancel (spec §9 — the two modes)
Deleting = set `status='cancelled'` (never DELETE). The **Delete** control must offer:
- **Delete this instance** → `cancelReservationsByGroup(groupId)` — cancels just this
  occurrence's rows.
- **Delete the whole series** (only shown when the booking has a `series_id`) →
  `cancelReservationsBySeries(seriesId)` — cancels all rows in the series. Per spec §9 this
  "typically only [affects] future occurrences; leave past ones as history" — if the repo's
  `cancelReservationsBySeries` doesn't already scope to future occurrences, either add a
  scoped variant/param or document the chosen behavior explicitly in the report (don't
  silently cancel historical rows without saying so).
- For a **one-off** booking, only the single "cancel this booking" action is shown.
- Confirm destructive actions in the UI (a confirm step / modal). The server action is the
  real guard — the UI confirm is courtesy.

### 2.5 Audit every mutation
- `writeAuditLog` for **each** action — contact edit, line/date edit (cancel-then-rebook),
  cancel-instance, cancel-series — with `before`/`after` detail and `entity_id`, **inside the
  same transaction** as the mutation, actor = the `requireScheduler()` caller. Mirror P6.1's
  audit call shape.

### 2.6 Domain conventions to respect
- Time is **minutes since Eastern local midnight**; convert via `easternInstant` (never store
  offsets, never use floats). Money isn't edited here. `status='cancelled'` frees capacity via
  the partial index — that's why cancel-then-rebook is safe.

## 3. Testing (REQUIRED — do not skip)

The **Tests** slice (§6, Slice D) is a `test-engineer` subagent (pass `model: opus`) working
its **own** file(s) under `tests/` against the contract from Slice A. Match the existing

**Server-action / repository-level (mocked `pg`):**
- **Contact/notes edit** updates the right rows, does **not** call the booking engine, and
  writes an audit row.
- **Line/date/time edit (cancel-then-rebook):**
  - happy path — old rows cancelled + new rows created in one txn + audit written;
  - moving to a window with capacity → succeeds; moving to a **full** window →
    `GroupBookingConflictError` → transaction rolls back, original booking unchanged, no
    audit committed, conflict lines returned;
  - editing one occurrence of a series preserves `series_id`.
- **Delete this instance** cancels only that group's rows (`status='cancelled'`, not deleted),
  audits.

  offered for a one-off.

  (guard throws/redirects); assert explicitly per spec §3.
- **Zod validation** rejects: invalid email, bad time (end ≤ start, out of 0–1440), empty
  line set, missing required fields.
- **Load** — `getReservationGroupById` miss → `notFound()`.

## 4. Guardrails (non-negotiables)

- **`import "server-only"`** in any module touching the DB or secrets.
- **No DDL, no deploy, no touching `.env.local`, no `git merge`.** This task needs **no
  schema change** — the tables and repo functions already exist. Build/verify on a branch and
  STOP; a human runs the merge.
- **Every capacity-affecting edit goes through `scheduler.createBooking`** (§8 race safety) —
  never a plain UPDATE of dates/items/quantities. This is the one rule that protects the
  shared production tables.
- **Cancel, never DELETE** (`status='cancelled'`).
- Wire `writeAuditLog` into **every** mutation; mutation + audit share one transaction.
- **Launch every `code-writer`/`test-engineer` subagent with `isolation: "worktree"`** and
  pass **`model: opus`** (the pinned `claude-sonnet-4-5` is unavailable here). Wave-2 lesson:
  a shared working tree scrambles branch pointers — one tree = one branch pointer they fight
  over. Per-slice worktrees are mandatory for the parallel wave (§6).
- **The slices in §6 are designed to not edit the same file.** If a subagent finds it needs
  to change a file another slice owns, it must stop and report the collision to the
  work-distributor rather than editing it — the distributor reconciles at integration time,
  or serializes those two slices. Never let two concurrent agents edit one file.
- Match the P6.1 code style. Don't duplicate the scheduler/product surface — consume the
  existing `lib/scheduler/*` and `@bcc/scheduler`.

## 6. Suggested distribution (work-distributor: this is your plan)

The obvious files (`page.tsx`, `actions.ts`, the form component) are tightly coupled, so
naive fan-out collides. Split instead into **one contract slice first, then three parallel
slices** that each own **disjoint files** and depend only on the shared contract. Every
subagent runs in its **own worktree** with **`model: opus`**.

### Slice A — Shared contract (do FIRST; blocks the rest) · `code-writer`
Owns a **new, small** contract/types module that the other slices import — e.g.
`app/reservations/[groupId]/types.ts` (result-state shape + input types) and, if useful, a
thin `loader.ts` (the read path: `getReservationGroupById` + `listReservationsByGroup` +
optional series). Deliverables:
- The `useActionState`-shaped result type (`status`/`message`/`fieldErrors`/`conflicts`/…),
  mirroring P6.1's `CreateReservationState` + `ConflictLine`.
- Input types for the three edit operations (contact-edit, line/date-edit, delete-mode).
- The Zod field rules shared by validation (or their schema), so UI and actions agree.
- The read/loader function(s) the page will call.
This slice is deliberately tiny and **fast**; the other three start the moment it lands (the
distributor merges Slice A into the integration branch and rebases/branches the others from
it, **or** shares it as a committed base). Nothing else may edit these files.

### Slice B — Server actions · `code-writer` (parallel, after A)
Owns `app/reservations/[groupId]/actions.ts` **only**. Implements, per §2:
- contact/notes edit (no engine), line/date/time edit via **cancel-then-rebook** through
  `scheduler.createBooking` in one txn, delete-instance, delete-series;
- `requireScheduler()` first, `writeAuditLog` inside each txn, `isRedirectError` re-throw.
Imports types/loader from Slice A. Does **not** touch the page or form files.

### Slice C — Page + form UI + calendar entry point · `code-writer` (parallel, after A)
Owns `app/reservations/[groupId]/page.tsx`, its form component + `page.module.css`, **and**
the one-line calendar change that links a booking bar to `/reservations/[groupId]`
([app/calendar/*](../../app/calendar)). Renders the loaded booking, wires the form to the
Slice B actions **via the Slice A types** (import the action functions by name; if B isn't
merged yet, code against the shared signatures and the distributor resolves the import at
integration). Confirms destructive actions in the UI. Does **not** touch `actions.ts`.
> If the calendar file turns out to be shared with another in-flight task, Slice C flags it
> to the distributor rather than editing blind.

### Slice D — Tests · `test-engineer` (parallel, after A) 
Owns **new** files under `tests/` only (e.g. `tests/reservation-edit-actions.test.ts`).
Writes the full §3 matrix against the Slice A contract + Slice B action signatures (mock
`pg`, mirror existing suites). Because it only adds files, it never collides; it may be
authored against B's branch once B has a first commit.

### Integration (work-distributor)
1. Land Slice A. 2. Run B, C, D concurrently (own worktrees). 3. Assemble
`integration/p6.2-edit-reservation` = A + B + C + D; resolve the (small, expected) import
seams between C→B and D→B. 4. Run the §5 gates on the combined tree. 5. STOP and report; a
human merges.

**Fallback:** if the contract seams prove too chatty to be worth the parallelism (this is a
medium-sized task), the distributor may collapse to **A → then a single `code-writer` for
B+C** with **D in parallel** — still faster than fully serial, and collision-free. Use
judgment; report which shape was used.
