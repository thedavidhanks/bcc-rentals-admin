## 2. Functional requirements (the spec, made concrete)

Build an **admin-only** Users page + its server actions that support:

1. **List users** — show all `app_users` (both active and inactive; visually distinguish
   inactive). Columns: name, email, role, active, last login. Order as the repo returns
   (role, then email). Schedulers must never reach this page (server-enforced).
2. **Set role** — toggle a user between `scheduler` and `admin` (`updateUserRole`).
3. **Deactivate / reactivate** — `setUserActive(uid, false|true)`. **Deactivate, never
   delete** (CLAUDE.md). Deactivated users are denied at login by the existing guard.
4. **Invite a user by email** — an admin adds an account by **email + name + role** (NO
   UID). This creates a **pending invite** row (see §2A for storage + binding). The person
   later signs in with Firebase using that email; on first sign-in the server binds their
   real UID to the invite and activates the account. The Users page must (a) let an admin
   create an invite, (b) show pending invites distinctly from bound users, and (c) let an
   admin revoke a pending invite. Store email lowercased. See **§2A** for the full mechanic
   and the two locked security decisions.
5. **Last-active-admin guard (CRITICAL — this is the corruption/lockout guard):** the
   system must **never** end up with zero active admins. Block, at the **server action**
   level (not just UI), any operation that would remove the last active admin:
   - demoting the last active admin to `scheduler`,
   - deactivating the last active admin,
   - (defensively) an admin acting on their own account in a way that self-locks-out.
   Implement this **inside the same transaction** as the mutation: perform the change, then
   `countActiveAdmins(client)` and **throw/rollback** if the count would be `0`. Do the
   pre-check with a clear error message too, but the transactional re-check is the real
   guard against a race between two admins. Return a friendly, specific error to the UI.
6. **Custom-claim re-sync (OPTIONAL / best-effort):** the spec marks Firebase custom claims
   as an *optional* fast-path and the DB row remains authoritative; middleware here is
   currently cookie-presence-only and does **not** read claims. **Do not block delivery on
   this and do not refactor `lib/auth/session.ts`'s private `getAdminAuth()` just for it.**
   Leave a `// TODO(P6.6): optional custom-claim mirror` at the role-change site with a
   one-line note on how it would attach. If the assigned agent can add it cleanly and
   best-effort (failure must NOT fail the DB mutation), that's a nice-to-have — otherwise
   defer. Call this out explicitly in the final report.
7. **Audit every mutation** — `writeAuditLog` for add/role-change/activate/deactivate with
   `before`/`after` detail, inside the transaction, actor = the `requireAdmin()` caller.

**Domain conventions to respect:** roles are exactly `'scheduler' | 'admin'` (DB check
constraint); email stored lowercased; `updated_at` handled by the repo. No money/time
concerns in this task.

## 2A. Invite-by-email onboarding (the extension — read carefully)

**Why:** typing a 28-char Firebase UID by hand is error-prone and bad UX. Instead an admin
invites by **email**; the UID is bound automatically on first sign-in. The person just signs
in — no UID handling by any human.

**Spec-§3 reconciliation (important):** spec §3 says *"do not rely on the email as the key."*
We honor that — **UID remains the durable, canonical key.** Email is used **once**, only to
match a pending invite to a signing-in user, after which the UID is authoritative forever.
Document this reasoning in a code comment at the binding site so a future reader doesn't
think §3 was violated.

### Two locked decisions (from the human — do NOT re-litigate)

1. **Binding requirement = `email_verified` only.** Bind a signing-in user to a pending
   invite **only if** the Firebase token's `email_verified === true` AND the (lowercased)
   token email exactly equals the invite email. Do **not** additionally re-gate on
   `ALLOWED_EMAIL_DOMAIN` at the bind site — the existing guard already enforces the domain
   downstream. An unverified-email sign-in must **not** bind (prevents invite takeover).
2. **Storage = make `app_users.uid` nullable.** A pending invite is a real `app_users` row
   with `uid = NULL`, `active = false`, `role` preset by the admin, `email`/`name` set.
   - **Schema change** in [db/schema.sql](../../db/schema.sql): make `uid` nullable while
     keeping uniqueness for non-null values. Use an **idempotent** migration:
     `ALTER TABLE app_users ALTER COLUMN uid DROP NOT NULL;` and replace the plain
     `UNIQUE(uid)` with a **partial unique index** so multiple `NULL` invites can coexist:
     `CREATE UNIQUE INDEX IF NOT EXISTS app_users_uid_key ON app_users (uid) WHERE uid IS NOT NULL;`
     (the original inline `UNIQUE` on the column also creates a constraint — reconcile so the
     final state is: nullable `uid`, uniqueness only over non-null values; write it so
     re-running is safe on a branch that already has the old constraint). Also add a partial
     unique index on `lower(email)` for **pending** invites so you can't create two open
     invites for the same address. **DDL is human-applied, dev-branch first** — you write it,
     a human runs `npm run db:apply` (dev), then prod under approval. Call this out in the
     report as a required human step.

### Repository additions (in [lib/repositories/app-users.ts](../../lib/repositories/app-users.ts))

Add typed functions — no raw SQL elsewhere:
- `createInvite({ email, name, role }, client?)` → inserts a pending row (`uid=NULL`,
  `active=false`). Reject (or upsert-revive) if an open invite already exists for that email.
- `getPendingInviteByEmail(email, client?)` → the open invite for an email, or null.
- `bindInvite({ email, uid, name?, client? })` → atomically attach the UID, set
  `active=true`, refresh name/last_login, on the matching pending row; return the bound row
  or null if none matched. Must be safe under concurrency (one invite → one bind).
- `revokeInvite(id, client?)` (or reuse deactivate semantics) for an admin to cancel a
  pending invite.
- Update `listUsers` (or add a variant) so the UI can separate **pending** (uid null) from
  **bound** users. Keep the `AppUserRow` type honest — `uid` is now `string | null`.

### Binding hook (login flow)

- Thread `email_verified` from the decoded Firebase token through `verifyRealSession()` →
  `SessionIdentity` ([lib/auth/session.ts](../../lib/auth/session.ts),
  [lib/auth/types.ts]). The dev-bypass path can treat its stub as verified.
- In `getSessionUser()` ([lib/auth/guards.ts](../../lib/auth/guards.ts)): after
  `getUserByUid(uid)` returns **null** (unknown UID) and **only** when
  `identity.email_verified === true`, attempt `bindInvite({ email, uid, ... })`. If it binds,
  proceed as that user; if not, keep today's behavior (deny → null). This preserves the
  "deny unknown users, no auto-provisioning of *roles*" posture: a stranger who signs in with
  no matching invite still gets nothing.
- **Audit the bind** (`writeAuditLog`, action e.g. `user.invite.bind`, actor = the binding
  user themselves or `system`). Keep the whole bind + audit in one transaction.
- The binding write must be **idempotent / race-safe**: two concurrent first-sign-ins (or a
  double request) must bind at most once; a UID already bound must not re-bind or steal
  another invite.

### Pending-user experience

A signed-in user whose invite hasn't been created/bound sees the existing "denied" behavior.
(An "awaiting approval" screen is **out of scope** — with invite-by-email the admin acts
first, so a matched user is active immediately on sign-in. Do not build a pending-state
landing page.)

Testing is part of the deliverable, not an afterthought. Assign a **test-engineer**
subagent (pass `model: opus` — the pinned `claude-sonnet-4-5` is unavailable here) to cover:

**Unit / server-action tests (mocked `pg`, like the existing suites):**
- Setting a role updates it and writes an audit row.
- Deactivate / reactivate flips `active` and audits.
- **Invite by email** — creates a pending row (`uid=NULL`, `active=false`), audits; a second
  open invite for the same email is rejected (or revives, per your choice); admin revoke
  works.
- **Invite binding (the security-critical path):**
  - first sign-in with `email_verified=true` and a matching pending invite → binds UID, sets
    `active=true`, audits, user becomes authorized;
  - `email_verified=false` with a matching invite → does **NOT** bind, user denied;
  - signed-in email with **no** matching invite → denied, no row created (no
    auto-provisioning);
  - a UID already bound to a user → never re-binds / never steals a different invite;
  - concurrency: two simultaneous binds resolve to a single bound row (assert the repo/guard
    guards against double-bind).
- **Last-admin guard** — every path is covered and rejects:
  - demote the only active admin → rejected, no write, no audit committed;
  - deactivate the only active admin → rejected;
  - with **two** active admins, demoting/deactivating one → allowed;
  - the transactional re-check rolls back (simulate the count dropping to 0).
- **Authorization** — a `scheduler` (or unauthenticated) caller hitting each action is
  denied server-side (guard throws/redirects); assert this explicitly per spec §3.
- Zod validation rejects: empty/blank UID, invalid email, invalid role.

**UI / functional verification:**
- The page renders the user list, distinguishes **pending invites** (uid null) from bound
  users and inactive users, and hides correctly for schedulers (server-side).
- Invite form + revoke control work; forms surface field-level and top-level errors via the

## 6. Suggested distribution

The invite-by-email extension makes this **more than a single UI file** — it touches the
schema, the repo, the login/session path, and the Users UI. These are **sequentially
dependent** (schema → repo → binding hook → UI), so a **single `code-writer`** owning the
whole branch (handing off to **test-engineer** via its built-in flow) is the lowest-risk
shape. Fanning out across the layers would create merge churn on shared files
(`session.ts`, `guards.ts`, `app-users.ts`) — avoid it.

Recommended:
- **Agent A (code-writer, worktree, model: opus):** does it end-to-end in dependency order —
  (1) schema migration in `db/schema.sql`; (2) repo functions (invite/bind/list); (3)
  thread `email_verified` + binding hook in `session.ts`/`guards.ts`; (4) Users page +
  server actions (invite, revoke, role, activate/deactivate) with the last-admin guard +
  audit. Owns the branch.
- **Agent B (test-engineer, model: opus):** authored against Agent A's branch — all tests in
  §3, with emphasis on the **binding security matrix** and the **last-admin guard**.

Integrate onto one branch, verify the **combined** tree (§5), hand off a single merge.
**Do not** parallelize across the four layers — they edit overlapping files.
