## 2. The deliverable

### 2.1 Schema — [db/schema.sql](../../db/schema.sql)

`app_users` is defined at `db/schema.sql:78-89`, with its partial unique indexes at `:97-104`.
Append, in the same idempotent style as the P6.6 reconciliation block already there:

```sql
-- P6.8: an admin-created invite is an explicit, per-person vetting act, so an
-- invited account is exempt from the ALLOWED_EMAIL_DOMAIN second gate (spec §11)
-- for the life of the account — not just at the instant the invite binds.
-- Defaults to false: a row created by any other path (the one-time bootstrap
-- admin insert, a future provisioning path) stays domain-enforced.
ALTER TABLE app_users ADD COLUMN IF NOT EXISTS domain_exempt boolean NOT NULL DEFAULT false;
```

`DEFAULT false` is load-bearing — it is what keeps the wall up for everything that is not an
invite. Do not change it to `true`, and do not backfill existing rows.

- In **`createInvite`** (`:189-217`), set the flag on the INSERT. The current statement is

1. **The domain wall still holds for everyone else.** A non-domain email whose row is *not*
   `domain_exempt` is denied — on first sign-in and on every later one.
2. **`domain_exempt` is never client-settable.** It is not in any Zod schema, not read from

## 4. Judgment calls — already decided, do not re-litigate

### 4.1 Mechanism: a persisted column, **not** the "narrow the check" alternative

Issue #1 leaves two directions open. **Take the persisted-column direction (2.1–2.4).** The
reasoning, so you don't relitigate it mid-task:

- The durability problem is real and is the trap this task exists to avoid. `bindInvite`'s
  `WHERE uid IS NULL` (`lib/repositories/app-users.ts:230`) means the invite stops being *pending*
  the instant it binds. Any fix shaped like "check whether a pending invite exists for this email"
  passes once and then **locks the person out on their very next request** — and the first
  sign-in would look like a success, so it would ship. A stored per-account fact has no such
  window.
- The other direction (drop the per-request domain check entirely, on the argument that every
  `app_users` row is admin-created anyway) is *defensible* — but spec §11 line 510 calls this a
  guard **"on top of"** the `app_users` check, and removing the only place it is enforced deletes
  it in effect while leaving the env var in the table, which is worse than either keeping it or
  removing it honestly. It also makes a future non-invite provisioning path silently unguarded.
- Cost: one `ADD COLUMN IF NOT EXISTS boolean NOT NULL DEFAULT false`. Idempotent, instant, no
  rewrite, no downtime, and the apply workflow is already proven against both branches (P8.4).

**Flag this consequence loudly in your handoff** (it is expected, not a bug): the prod interim
admin `dphanks@gmail.com` was created by a manual bootstrap insert, so it gets
`domain_exempt = false` and **will be locked out the moment `ALLOWED_EMAIL_DOMAIN=bachmancc.org`
is set**. That is already the plan — CLAUDE.md requires the `@bachmancc.org` swap to land first —
but the human running the migration needs to see it written down.

### 4.2 One existing test asserts the bug. You must change it — this is the one sanctioned exception to "weaken nothing"

[tests/invite-binding.test.ts:140-150](../../tests/invite-binding.test.ts#L140-L150),
`"domain gate is re-applied to the bound email: disallowed domain → null"`, pins the current
behavior: an invitee at `invitee@evil.com` binds and is then denied. Under the fix, a **bound
invite row** carries `domain_exempt: true`, so that case must now **pass**.

Rewrite it as **two** cases, so coverage goes up rather than down:

- an invited non-domain address (bound row with `domain_exempt: true`) is **allowed**;
- a non-domain address on a row with `domain_exempt: false` is **still denied** — this is the old
  assertion's real intent, preserved.

Say explicitly in your handoff that you changed this test and why. Changing any *other* existing
assertion is out of bounds.

### 4.3 No UI, no invite-form checkbox

An invite is already the explicit per-person vetting act; every invite is exempt, with no admin
toggle. Do **not** add a checkbox to the invite form, a badge to the users table, or a column to
`app/users/*`. If you think the admin should be able to choose per-invite, that is a separate UX
decision — put it in your handoff as a suggested follow-up issue, don't build it.

### 4.4 Naming

Use `domain_exempt` (snake_case in SQL, and the same in `AppUserRow` — that interface mirrors DB
column names exactly, see `last_login` / `created_at`). Don't invent a camelCase alias.

**Harness constraint:** `vitest.config.ts` is `environment: "node"` with

You will need to extend the test harnesses, not just add cases:

  field; its `mockAll` (`:15-…`) hard-codes `bindInvite` to return `null`, so the *returning-user*
  cases belong here.
- [tests/invite-binding.test.ts](../../tests/invite-binding.test.ts) — `boundRow` (`:55-68`) and
  `activeRow` (`:70-83`) need the field; its `mockAll` (`:20-…`) already accepts `boundRow`, so the
  *first-sign-in bind* cases belong here. This is the right file for §4.2's rewrite.
- [tests/app-users-invite.test.ts](../../tests/app-users-invite.test.ts) — asserts `createInvite`'s
  emitted SQL by substring (`:110-111` checks the literal
  `VALUES (NULL, $1, $2, $3, false, now(), now())`). **That assertion will break when you change
  the INSERT** — update it to match the new tuple and add a case asserting the invite is created
  with `domain_exempt` true.
- [tests/repositories.test.ts](../../tests/repositories.test.ts) — `app_users repository` block
  starts at `:238`; check nothing there pins `USER_COLUMNS`.

Required cases, at minimum:

1. Invited non-domain email, **first** sign-in: binds and is **not** denied in that same
   `getSessionUser()` call.
2. That same user's **next** session — a fresh `getSessionUser()` where `getUserByUid` returns the
   bound `domain_exempt: true` row and `bindInvite` is never called — **still allowed**. *This is
   the case the naive fix gets wrong; if you only write case 1, you have not tested the task.*
3. Non-domain email, `domain_exempt: false`, no invite history: **denied**, on a fresh sign-in and
   on a repeat.
4. A domain-matching user (`domain_exempt: false`) is unchanged — still allowed.
5. `domain_exempt: true` **does not** rescue an inactive row, a `uid: null` row, or a UID with no
   row at all (§3.3).
6. `createInvite` emits `domain_exempt` true; `upsertUser` does not set it.
