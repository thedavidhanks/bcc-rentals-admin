## 2. Task specs

### P11.2 — Account menu with Logout (`code-writer`, worktree) — **PRIORITY**

**The bug:** [components/sign-out-button.tsx](../../components/sign-out-button.tsx) exists but is
**rendered nowhere**, so there is no way to sign out of the app.

**Deliver:** replace the plain user label
([AppNav.tsx:70](../../components/nav/AppNav.tsx#L70), `.app-nav__user`) with a **circular avatar
button in the top-right** (GitHub/Facebook style — an initials monogram) that opens a dropdown
containing at minimum:

- **Update profile** → `/profile`
- **Logout** → the existing sign-out flow

**Details that matter:**

- **The sign-out endpoint is `DELETE /api/auth/session`**, not POST — see
  [app/api/auth/session/route.ts](../../app/api/auth/session/route.ts) (`DELETE` clears the cookie;
  `POST` mints it). The EXECUTION_PLAN row says "POST … delete" — that wording is imprecise; the
  route is authoritative. Reuse the existing `SignOutButton` flow (`fetch(..., { method: "DELETE" })`
  → `window.location.assign("/login")`); restyle/relocate it into the menu rather than duplicating
  the fetch in a second component. A full-page navigation (not `router.push`) is deliberate — it
  discards all client caches of the signed-in tree.
- **Accessibility is part of the deliverable:** Esc closes, outside-click closes, `aria-expanded` /
  `aria-haspopup="menu"` on the trigger, `role="menu"`/`menuitem` on the items, focus moves into the
  menu on open and returns to the trigger on close, and focus stays trapped while open. Keyboard
  users must be able to log out.
- **Responsive:** the avatar must remain reachable at the mobile breakpoint (48rem) where the nav
  collapses to the hamburger — it should sit in the top bar, not inside the collapsed menu. Follow
  the existing `.app-nav__*` BEM-ish class convention and the `--nav-*` custom properties in
  [app/globals.css](../../app/globals.css); no CSS framework, no new dependency.
- **Monogram source:** `SessionUser` today is `{ uid, role, email }` only — **there is no `name`**
  ([lib/auth/types.ts](../../lib/auth/types.ts)). See §4 for the recommended call.
- `AppNav` is a client component and **makes no security decisions** — keep it that way. It renders
  what the server hands it.

### P11.1 — Nav must show only what the role can reach (`code-writer`, worktree)

**The bug:** signing in as a `scheduler` and clicking **Products** throws
`ForbiddenError: Admin role required` — [app/products/page.tsx:29](../../app/products/page.tsx#L29)
calls `requireAdmin()`, but the Products entry at
[components/nav/nav-config.ts:19](../../components/nav/nav-config.ts#L19) has no `adminOnly: true`.

**Deliver:**

1. Fix the Products entry.
2. **Audit every row in `NAV_ITEMS`** against the guard the destination page actually calls. Current
   ground truth (verified 2026-09-03 — re-verify, don't trust this table blindly):

   | Nav entry      | Route              | Page guard         | `adminOnly`?          |
   | -------------- | ------------------ | ------------------ | --------------------- |
   | Calendar       | `/calendar`        | `requireScheduler` | no                    |
   | Products       | `/products`        | **`requireAdmin`** | **yes — the bug**     |
   | Add Reservation| `/reservations/new`| `requireScheduler` | no                    |
   | Update Prices  | `/prices`          | `requireScheduler` | no                    |
   | Categories     | `/categories`      | `requireAdmin`     | yes (already correct) |
   | Users          | `/users`           | `requireAdmin`     | yes (already correct) |

3. **Add a test that stops the two from drifting again** — the real deliverable. Assert that every
   `NAV_ITEMS` entry is reachable by the roles it is shown to. Preferred: a static parity test that
   resolves each `href` to its `app/**/page.tsx` and asserts `requireAdmin` in the file ⟺
   `adminOnly: true` on the entry (read the files with `node:fs`, match the guard call — the pages
   `await requireAdmin()` / `await requireScheduler()` in a stable shape). If that proves brittle,
   fall back to an explicit `ROUTE_GUARDS` map in the test asserted against `NAV_ITEMS`, but say why

4. **Update the existing test** — [tests/nav-config.test.ts](../../tests/nav-config.test.ts) asserts

**Out of scope for P11.1:** changing any page's guard. If a page's guard looks *wrong* (e.g. you

## 3. Cross-cutting requirements (both tasks)

- **The server guards remain the only real access boundary.** Everything here is the cosmetic half.
  No subagent may weaken, remove, or route around `requireScheduler`/`requireAdmin`.
- **No schema change, no DDL, no deploy, no new dependency.** Neither task needs any. If a subagent
  believes it needs one, that is a red flag: stop and surface it to you, and you surface it to the
  human.
- **No mutation → no audit write is expected here.** (Profile *writes* are P11.3, not this wave.)
  If P11.2 ends up writing anything to the DB, that's out of scope — stop and surface it.
- **Test harness constraints (read before planning tests):** `vitest.config.ts` uses
  `environment: "node"` and `include: ["tests/**/*.test.ts"]` — **`.tsx` files are not collected,
  and there is no jsdom / `@testing-library/react` installed.** So:
  - Do **not** add jsdom or testing-library. That is a dependency + config change; if a subagent is
    convinced DOM-level tests are essential, it must stop and surface it rather than install.
  - Instead, **extract the testable logic out of the component into a plain `.ts` module** and unit
    test that — e.g. initials/monogram derivation from `name`/`email` (empty string, no `@`,
    single-word name, unicode, very long name), and the account-menu item list for each role. Match
    the existing suite style (mocked `pg` where DB is involved; none should be here).
- Each `code-writer` hands its branch to `test-engineer` for verification before you integrate
  (launch it as-is on its pinned `claude-sonnet-5` — **no** `model:` override).
- Per branch and again on the integration branch: `npm run typecheck`, `npm run lint`, `npm test`
  must all pass. The baseline on `master` is **418 tests / 25 files** — the combined tree must be
  ≥ that, with no pre-existing test deleted to make a new one pass.
