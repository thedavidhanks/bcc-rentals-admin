# Work Order — P11.9 + P11.10: Add Reservation — shared "When" box, and stop wiping the form on error

**For:** the `code-writer` agent. **One agent, one worktree, sequenced** — P11.9 first, then P11.10
on top of it.

**Deliver by:** implementing both tasks on a single branch, handing the branch to `test-engineer`
for verification, and stopping **before merge** (merge to `master` is human-gated in this repo).

**Why this one is next:** Add Reservation is the highest-traffic staff flow, and today it is the
worst one to use. Every line item asks for its own Date/Start/End even though all items in a
booking share one window (spec §7 "the shared or per-item date/time window"), so booking an
auditorium + 200 chairs means typing the same date and times three times. And when the submit is
rejected — a validation slip, or an all-or-nothing capacity conflict, which is *routine* on a busy
calendar — every field resets to empty and the user retypes the whole booking. Both defects live in
the same file and P11.10 must echo back the shared window P11.9 introduces, so splitting them means
guaranteed conflict and rework.

## 2. The deliverable — P11.9: one shared date/time for the whole booking

### 2.1 Form field contract (decide once, apply everywhere)

Today every line carries its own window: `line-<i>-date`, `line-<i>-startMinute`,
`line-<i>-endMinute` (see
[reservation-form.tsx:141-167](../../app/reservations/new/reservation-form.tsx#L141-L167) and the
collector at
[actions.ts:129-149](../../app/reservations/new/actions.ts#L129-L149)).

**New contract — use exactly these names:**

| Field | Name | Notes |
| --- | --- | --- |
| Shared date | `date` | Eastern civil date `YYYY-MM-DD` |
| Shared start | `startMinute` | HTML `<input type="time">` `HH:MM` |
| Shared end | `endMinute` | same |
| Per line | `line-<i>-itemSlug`, `line-<i>-quantity` | **unchanged** |

Per-line date/time inputs are **removed**, not hidden. Recurrence field names
(`recurring`, `recurrence-*`) are **unchanged**.

### 2.2 `reservation-form.tsx` — layout

- New `<fieldset className={styles.section}>` with `<legend>When</legend>`, rendered **above** the
  "Line items" fieldset, containing the Date / Start / End inputs **and** the existing recurrence
  toggle + recurrence controls moved into it verbatim (the plan row says "keep the recurrence
  controls with it"). The separate "Recurrence" fieldset goes away; its markup and field names
  survive intact inside the "When" box.
- The Date input seeds from the existing `defaultDate` prop (the `?date=` deep link honored by
  [page.tsx:25-27](../../app/reservations/new/page.tsx#L25-L27)) — **that deep link must keep
  working**.
- The line-item row drops three inputs and keeps Product / Qty / remove. Add/adjust
  `page.module.css` classes as needed (`.whenGrid` or similar) — plain CSS Modules, matching the
  file's existing style. **No CSS framework, no new dependency.**
- Render field errors for the new paths (`date`, `startMinute`, `endMinute`) next to those inputs,
  the way `fieldError("lines")` is rendered today.

### 2.3 `actions.ts` — parsing and booking

- **`requireScheduler()` stays the very first statement.** Do not move it, do not weaken it.
- `lineSchema` loses `date` / `startMinute` / `endMinute` and its two `.refine()`s; those move to
  the form-level schema: `date` (DATE_RE), `startMinute` / `endMinute` (the existing `timeString`
  transform to minutes), plus **`endMinute > startMinute`** (path `["endMinute"]`) and

- `buildGroup` now applies the single shared window to every line. The `perLineDate` parameter and

- Recurring: the series anchor `startsOn` is `parsed.date` (it was `sort()[0]` over the per-line

## 3. The deliverable — P11.10: echo the submitted values back on failure

### 3.1 A testable seam (this is the part that makes it verifiable)

`vitest` does **not** collect `.tsx` (see §5), so the echo logic must not live in the client
component. Create a **new plain module** `app/reservations/new/form-values.ts` — no `"use server"`,
no `server-only`, no DB imports, importable from both the action and the client:

- `export interface SubmittedValues` — **raw strings exactly as submitted**: `date`, `startMinute`,
  `endMinute`, `title`, `contactName`, `contactEmail`, `contactPhone`, `notes`, `recurring:
  boolean`, `recurrence: { freq; interval; byWeekday: string[]; endMode; untilDate; count }`, and
  `lines: { itemSlug: string; quantity: string }[]`.
- `export const EMPTY_SUBMITTED_VALUES: SubmittedValues` — one empty line row, sensible defaults
  (`quantity: "1"`, `interval: "1"`, `count: "4"`, `endMode: "count"`, `freq: "weekly"`) matching
  today's `defaultValue`s.
- `export function readSubmittedValues(formData: FormData): SubmittedValues` — this **replaces**
  `readForm` in `actions.ts`. Same index-scanning logic (`/^line-(\d+)-/`, sorted, non-contiguous
  indices tolerated).

**Raw strings, not parsed values** — the echo has to survive a *failed* parse, so it must be
captured before/independently of Zod. Feed the same object into `formSchema.safeParse(...)` (adapt
the schema's input shape to it; keep `recurrence` passed as `undefined` to validation when
`recurring` is false, while still echoing the raw recurrence fields back).

### 3.2 `types.ts` — the state

Add to `CreateReservationState`:

```ts
/** Raw values from the last submission, echoed back so a rejected save does
 *  not wipe the form (P11.10). Undefined = no submission yet. */
values?: SubmittedValues;
```

Document it with the same reasoning as [app/profile/state.ts](../../app/profile/state.ts). Keep
`types.ts` free of server imports — it is imported by the client component.

### 3.3 Every failure path echoes

**Every** `return { status: "error", ... }` in `createReservationAction` carries `values` —
all of them:

1. Zod validation failure ([actions.ts:227-237](../../app/reservations/new/actions.ts#L227-L237))
2. unknown/inactive item slugs ([actions.ts:246-251](../../app/reservations/new/actions.ts#L246-L251))
3. recurrence expanded to zero occurrences ([actions.ts:273-278](../../app/reservations/new/actions.ts#L273-L278))
4. `GroupBookingConflictError` — the capacity conflict, **the most important one**
5. `SchedulerError`
6. the generic catch-all

The `isRedirectError(err)` re-throw at
[actions.ts:352](../../app/reservations/new/actions.ts#L352) stays exactly as-is — success still
redirects and carries no echo.

### 3.4 `reservation-form.tsx` — render the echo

- Seed `useActionState` and local state from `state.values ?? EMPTY_SUBMITTED_VALUES` (with
  `defaultDate` still seeding the date on first render).
- **Make the echoed fields controlled inputs** — `value` + `onChange` off local state, not
  `defaultValue`. Uncontrolled fields get reset by React after a Server Action completes; that is
  precisely the bug. This applies to the shared date/start/end, every contact field, notes, title,
  and each line's product + quantity.
- **Line rows must be reconstructed from the echo**: if the user submitted four line items and it
  failed, four rows with their values come back — not one empty row. Rebuild `rowIds` from the
  echoed `lines.length` when a new `state.values` arrives.
- Recurrence state (`recurring`, `freq`, `endMode`, checked weekdays, interval, count, untilDate)
  must round-trip too — a rejected recurring booking must come back still recurring, with the same
  rule.

## 4. Domain requirements — non-negotiable, each needs a test

1. **`requireScheduler()` is the first statement of the action**; a rejecting guard means no
   `listItems` call, no `withTransaction`, no audit row.
2. **The race-safe path is unchanged** — one transaction, per-item advisory locks in stable slug
   order, capacity re-check, all-or-nothing. The existing assertions in
   `tests/add-reservation-action.test.ts` that prove this must survive (renamed form fields are
   fine; **weakened assertions are not**).
3. **The audit row is written on the same transaction client as the booking**, action string
   `"reservation.create"` — assert client identity, not `expect.anything()`.
4. **Time stays minutes-since-Eastern-midnight**; instants are built with `easternInstant(date,
   minutes)`. No UTC offsets, no `Date` string math, no floats.
5. **The echo never leaks into a success/commit path** and never becomes an input to the write —
   it is display state only. In particular the echoed `itemSlug`s are still re-validated against
   the active catalog on the next submit.

## 7. Judgment calls — decide these, don't stall on them

1. **No backward compatibility for `line-<i>-date`.** The only client of this action is the form
   you're rewriting. Don't accept both shapes; don't add a fallback. Update the tests instead.
2. **Recurrence lives inside the "When" box** as a sub-section, not a sibling fieldset. Field names
   unchanged so the action's recurrence parsing is untouched.
3. **Controlled inputs, not `key`-remount tricks.** Follow the `/profile` precedent; it is the
   pattern this repo has already settled on and commented.
4. **Echo raw strings, never Zod output.** A submission that fails validation has no Zod output.
5. **Quantity stays per line** — only the *time window* is shared. Products and quantities remain
   per line item.
6. **Do not add a "different time per item" escape hatch.** Spec §7 permits shared-or-per-item; the
   product decision (P11.9) is shared. Simpler form, simpler action.
7. If the shared window makes an existing test's scenario meaningless (e.g. one asserting two lines
   on *different* dates in one group), convert it to the closest still-meaningful scenario and
   **call it out in your report** — don't silently drop coverage.
