## 2. The deliverable

### 2.1 Route — `app/profile/page.tsx`

- **Guard: `requireScheduler()`** — called **first**, before any DB work. Both roles may use the
  page, and `requireScheduler` already admits `admin` (see
  [lib/auth/guards.ts](../../lib/auth/guards.ts)). Do **not** invent a new guard.
- `export const dynamic = "force-dynamic"` and **defer the DB import** (`await import(...)`
  inside the loader) so `next build` stays free of `DATABASE_URL` / env boot validation — copy
  the header comment + pattern from [app/users/page.tsx](../../app/users/page.tsx#L1-L10).
- Load the caller's own row with `getUserByUid(user.uid)` from
  [lib/repositories/app-users.ts](../../lib/repositories/app-users.ts).
- Render:
  - **Editable:** `name` (single text input).
  - **Read-only:** role (rendered as a human label — see §4.1), email, and — your call —
    `last_login` (format with `Intl.DateTimeFormat` in `America/New_York`, as
    [app/users/page.tsx:12-16](../../app/users/page.tsx#L12-L16) does). Email is **not**
    editable: it comes from the identity provider and is display/contact only (spec §3).
  - Wrap the load in the same `try`/`catch` → `loadError` pattern the users page uses, so a DB
    hiccup renders a message instead of a stack trace.
- Style with a `page.module.css` alongside the page, matching the conventions of the other
  admin pages. No CSS framework, no new dependency.

### 2.2 Server action — `app/profile/actions.ts`

`"use server"` + `import "server-only"`. **This is the security-critical half — read §3 before
writing it.**

- `requireScheduler()` **first**, before parsing anything. The returned `user.uid` is the **only**
  key the write may use.
- Zod-validate the name: `z.string().trim().max(200)`; decide and document whether empty string
  clears the name (→ `null`) or is rejected — clearing to `null` is the recommended behavior
  (`app_users.name` is nullable and the monogram already falls back to email).
- One `withTransaction` containing **both** the `UPDATE` and the `writeAuditLog` call, so they
  commit atomically (`client` threaded into both — see
  [lib/repositories/audit-log.ts](../../lib/repositories/audit-log.ts) header).
- Audit entry: `actor_uid` = the caller's uid, `actor_email` = their email, `action` =
  `"user.profile.update"` (follow the existing dotted convention — `user.invite.bind` etc.),
  `entity` = `"app_users"`, `entity_id` = the row's `id`, `detail` = `{ before: { name }, after:
  { name } }`.
- `revalidatePath("/profile")` **and** revalidate the layout (`revalidatePath("/", "layout")`)
  so the account-menu monogram refreshes after a name change. Verify the call actually does that
  in this Next version; if it does not, say so rather than shipping a no-op.
- Return a `ProfileActionState` (typed in `app/profile/state.ts` — a `"use server"` file may only
  export async functions, hence the separate file, exactly as `app/users/state.ts` does) that
  **echoes the submitted name back** on failure so a rejected save does not wipe the field. (Same
  defect class as P11.10; fix it here at birth.)

### 2.3 Repository — `lib/repositories/app-users.ts`

Add one narrowly-scoped function, e.g.:

```ts
export async function updateUserName(
  uid: string,
  name: string | null,
  client?: Queryable,
): Promise<AppUserRow | null>
```

- `UPDATE app_users SET name = $2, updated_at = now() WHERE uid = $1 RETURNING <USER_COLUMNS>`.
- It must set **only** `name` and `updated_at`. `role`, `active`, `email`, `uid` are untouched —
  a self-service path must never be able to reach them.
- Returns `null` when no row matched (0 rows). Follow the file's existing style: `executor(client)`,
  the shared `USER_COLUMNS` constant, a short doc comment.

## 3. Security requirements — non-negotiable, verify each with a test

These are the reasons this task is worth a work order at all. A self-service editor that can be
coaxed into writing someone else's row, or its own `role`, is a privilege-escalation bug.

1. **Never accept a target user identifier from the client.** No `uid`, no `id`, no `email` read
   out of the `FormData` and used for the lookup or the `WHERE`. The write is keyed **only** off
   `(await requireScheduler()).uid`. Test: submit a `FormData` containing `uid=someone-else` /
   `id=<other row>` and assert the repository was called with the **session** uid.
2. **`role` and `active` are never written by this path.** Test: assert the update helper is
   called with only `(uid, name)`, and (repository-level, with a mocked `pg`) that the emitted SQL
   sets `name` + `updated_at` and nothing else.
3. **Guard runs before parsing.** Test: `requireScheduler` rejecting (throws / redirects) means
   no repository call and no audit write happened.
4. **Every mutation is audited, in the same transaction.** Test: the audit write receives the
   transaction `client`, and a thrown error inside the transaction leaves no partial state.
5. **The server guards remain the only real access boundary.** No subagent may weaken, remove, or
   route around `requireScheduler`/`requireAdmin` anywhere.

## 4. Judgment calls — decide these, don't stall on them

1. **"role/group" in the plan row is one field, not two.** Spec §3 line 107 labels
   `app_users.role` as *"Permissions (group)"*. There is **no** separate group column and none is
   to be added. Render the role read-only with a friendly label (e.g. `Scheduler` / `Admin`) and,
   optionally, a one-line "contact an admin to change this" hint.
2. **Dev-bypass sessions have no `app_users` row.** Locally with `AUTH_DEV_BYPASS`,
   `getSessionUser()` short-circuits on the stub role and `getUserByUid` will return `null` —
   so a naive page throws and a naive save silently updates 0 rows.
   **Recommended:** when no row is found, render the page with the session's email/role, disable
   the save control, and show a short explanatory notice; and have the action return a clean
   error state when `updateUserName` returns `null`. Do **not** create the missing row — this app
   never auto-provisions (spec §3).
3. **Do not add `/profile` to `NAV_ITEMS`.** It belongs in the account menu, where P11.2 already
   put it. [tests/nav-guard-parity.test.ts](../../tests/nav-guard-parity.test.ts) iterates
   `NAV_ITEMS` and asserts `adminOnly` ⟺ `requireAdmin` in the destination page; `/profile` is
   not a nav entry, so it should be unaffected — **confirm the test still passes** rather than
   assuming, and if the parity test enumerates pages rather than nav rows, extend it correctly
   (`/profile` = `requireScheduler`, not admin-only) instead of exempting the route.
4. **Sub-task split vs single agent** — see §1. Your call; report which you chose.
